# nD Sampling Designs for ABM Parameter Sweeps

This page documents the parameter-sweep tooling that currently exists in the repo. There are two related workflows:

- **ND grid runner**: `scripts/run_parameter_surface_nd_pnl_fee_dashboard.py`
- **General experiment runner**: `scripts/run_experiment_design.py`

They solve different problems:

- use the **ND grid runner** when you want an explicit Cartesian product, stable slicing by index, and a dashboard-oriented cache under `abm_results/grid_search/dashboard_nd/`;
- use the **experiment runner** when you want sampled designs (`lhs`, `sobol`, `sobol_saltelli`) or sequential designs (`adaptive_refine`, `bayesopt`) under `abm_results/experiments_runs/`.

## What Is Being Sampled?

For a parameter vector $\theta$ and RNG seed $s$, one simulator run returns a noisy draw:

$$
Y = f(\theta, s).
$$

You therefore choose both:

1. **Design points** $\theta_1, \dots, \theta_N$
2. **Replicates per point** $R$

The compute budget is roughly:

$$
\text{total simulator calls} \approx N \times R.
$$

The main tradeoff is breadth of parameter coverage versus Monte Carlo noise per point.

## Which Design Types Exist, And Where?

| Design type | Supported by | Notes |
| --- | --- | --- |
| `grid` | `core.experiment_design.py` and `scripts/run_experiment_design.py` | Requires explicit `values` for every parameter in the experiment YAML. |
| `lhs` | `core.experiment_design.py` | Static Latin Hypercube design. |
| `sobol` | `core.experiment_design.py` | Static quasi-random design. |
| `sobol_saltelli` | `core.experiment_design.py` | Static design for Sobol sensitivity analysis. |
| `adaptive_refine` | `scripts/run_experiment_design.py` | Sequential; not generated by the static core helper. |
| `bayesopt` | `scripts/run_experiment_design.py` | Sequential; not generated by the static core helper. |

Important distinction: `core.experiment_design.py` only generates the static designs. The sequential logic lives in the runner because it depends on previously observed results.

## Design Families

### Full-Factorial Grid

Choose an explicit value list for each parameter and evaluate the Cartesian product:

$$
N_{\text{grid}} = \prod_{k=1}^{d} n_k.
$$

Use grid designs when:

- you want clean slices or heatmaps in low dimension;
- the exact knot values matter;
- you want deterministic index slicing with `--index-start/--index-stop`.

Two grid paths exist in this repo:

- **dashboard ND grid** via `scripts/run_parameter_surface_nd_pnl_fee_dashboard.py`
- **experiment YAML grid** via `scripts/run_experiment_design.py` with `design.type: grid`

The experiment-YAML grid path is stricter: every parameter must provide explicit `values`. Continuous `bounds` alone are not enough for grid generation.

### Latin Hypercube Sampling (`lhs`)

Sample $N$ points in the unit hypercube so that each one-dimensional marginal is evenly stratified.

Use it when:

- you want a broad screening pass;
- dimension is moderate and a full grid is too expensive;
- you need a deterministic, space-filling static design.

### Sobol Sequence (`sobol`)

Use a low-discrepancy quasi-random sequence in $[0,1)^d$.

Use it when:

- you want better space-filling than naive random draws;
- you may later want to extend the design while keeping the same deterministic prefix;
- you are computing response surfaces rather than strict visual grids.

### Sobol-Saltelli (`sobol_saltelli`)

This design targets variance-based global sensitivity indices. If the base sample size is `n_base` and the number of parameters is $d$, the design size is:

$$
N_{\text{Saltelli}} = n_{\text{base}} (d + 2).
$$

Use it when the downstream goal is Sobol analysis, not just screening.

### Sequential Designs

Sequential designs adapt new proposals to the results already observed.

#### `adaptive_refine`

Uses an initial static design plus a surrogate model to add points in uncertain regions. If `regime_threshold` is supplied, it can bias proposals toward a boundary of interest.

Relevant YAML fields:

- `n_points`
- `n_init`
- `batch_size`
- `target_metric`
- optional `regime_threshold`

#### `bayesopt`

Uses a surrogate plus an acquisition rule to maximize or minimize one target metric.

Relevant YAML fields:

- `n_points`
- `n_init`
- `batch_size`
- `target_metric`
- `direction`

Important runtime constraints:

- sequential designs do **not** support `--index-start/--index-stop`;
- resume is stricter than for static designs: cached `point_id` values must be dense from `0..max_id`, otherwise the runner aborts rather than guessing how to continue.

## Mapping Unit-Cube Points To Real Parameters

For non-grid designs, the code samples a vector $u \in [0,1)^d$ and maps it parameter-by-parameter.

### Continuous Parameters

With linear scaling:

$$
x = \ell + u(h - \ell)
$$

With log scaling:

$$
x = \ell (h/\ell)^u
$$

Use log transforms for multiplicative scales such as rates or volatilities when you truly want equal spacing in log space.

### Discrete Parameters

With an explicit value list `(v_0, \dots, v_{k-1})`, the code maps:

$$
j = \lfloor uk \rfloor
$$

and selects `v_j` (optionally cast to `int` or `float`).

Practical implication: if a discrete parameter has only a few allowed values, LHS/Sobol points will still collapse onto those few values after transformation.

## Replication And Seed Semantics

At each design point the runner executes `runs_per_point` seeds.

Two seed modes exist:

- `common_seeds: false`
  - each point gets its own deterministic seed block;
  - for experiment designs the per-point seed base is derived from `seed_base + point_id * runs_per_point`;
- `common_seeds: true`
  - replicate `r` uses the same seed `seed_base + r` for every point;
  - this is useful for paired comparisons and variance reduction.

The tag/fingerprint system is also deterministic:

- experiment-design runs hash the parsed experiment YAML, the effective base-config content, and the script/schema version;
- ND grid runs hash the sweep definitions, integer-casting rules, seed mode, histogram settings, PnL summary kind, and effective config content.

Changing any of those inputs produces a new tag and therefore a new cache folder.

## ND Grid Runner Workflow

The dashboard grid runner writes global artifacts under:

```text
abm_results/grid_search/dashboard_nd/
```

Main files:

- `data/grid_<tag>.csv`
- `data/meta_<tag>.json`
- `data/errors_<tag>.csv`
- `data/config_snapshot_<tag>.yml`
- optional `data/sweep_config_snapshot_<tag>.yml`
- `logs/progress_<tag>.txt`
- worker temp runs under `_tmp_runs/<tag>/`

The HTML builder writes to `abm_results/grid_search/dashboard_nd/html/` by default.

### Sweep-Config YAML

The runner supports an optional sweep-config file via `--sweep-config`. The current helper supports:

- `values`
- `linspace`
- `geomspace`
- `linspace_int`
- `int_params`
- optional `fee_mode` override

That is the preferred way to define larger grid sweeps now; it is more reproducible than editing in-script defaults.

Minimal recipe:

```bash
conda activate main
python -m scripts.run_parameter_surface_nd_pnl_fee_dashboard \
  --config configs/scenarios/section4_microstructure_model0_static.yml \
  --sweep-config configs/scenarios/dashboard_nd_sweeps.yml \
  --dry-run
```

Run a slice:

```bash
python -m scripts.run_parameter_surface_nd_pnl_fee_dashboard \
  --config configs/scenarios/section4_microstructure_model0_static.yml \
  --sweep-config configs/scenarios/dashboard_nd_sweeps.yml \
  --index-start 0 \
  --index-stop 50 \
  --runs-per-point 10 \
  --max-workers 8
```

Build the dashboard:

```bash
python -m scripts.build_parameter_surface_nd_pnl_fee_dashboard \
  --cache abm_results/grid_search/dashboard_nd/data/grid_<tag>.csv \
  --meta abm_results/grid_search/dashboard_nd/data/meta_<tag>.json
```

## Experiment-Design Workflow

The experiment runner writes immutable tagged folders under:

```text
abm_results/experiments_runs/<tag>/
```

Main files:

- `data/points_<tag>.csv`
- `data/meta_<tag>.json`
- `data/errors_<tag>.csv`
- `data/base_config_snapshot_<tag>.yml`
- `data/experiment_snapshot_<tag>.yml`
- worker temp runs under `tmp/_tmp_runs/<tag>/`

The cache is append-only and restartable for static designs. The runner also exposes:

- `--max-workers`
- `--retry-failed`
- `--recompute`
- `--index-start` / `--index-stop` for static designs only

Minimal recipes:

```bash
conda activate main
python -m scripts.run_experiment_design \
  --experiment configs/experiments/example_lhs_screening.yml \
  --dry-run
python -m scripts.run_experiment_design \
  --experiment configs/experiments/example_lhs_screening.yml
```

Sobol-Saltelli example:

```bash
python -m scripts.run_experiment_design \
  --experiment configs/experiments/example_sobol_saltelli.yml
```

Sequential example:

```bash
python -m scripts.run_experiment_design \
  --experiment configs/experiments/example_adaptive_refine.yml \
  --max-workers 8
```

Build the dashboard:

```bash
python -m scripts.build_experiment_design_dashboard \
  --cache abm_results/experiments_runs/<tag>/data/points_<tag>.csv \
  --meta abm_results/experiments_runs/<tag>/data/meta_<tag>.json
```

If `--output` is omitted, the builder defaults to a sibling HTML file next to the cache (for example `<cache>.dashboard.html`).

## Analysis Workflow

`scripts/analyze_experiment_design.py` is a real downstream step, not just a conceptual add-on. It can write:

- `analysis/summary.json`
- permutation-importance CSV/HTML
- convergence HTML
- top-point CSV
- `sobol_<metric>.csv` when the design is `sobol_saltelli`
- optional regime-boundary candidate exports

Example:

```bash
python -m scripts.analyze_experiment_design \
  --cache abm_results/experiments_runs/<tag>/data/points_<tag>.csv \
  --meta abm_results/experiments_runs/<tag>/data/meta_<tag>.json \
  --metric fee_mean \
  --direction maximize
```

## Practical Guidance

- Use **grid** when you want interpretable slices and exact knots.
- Use **lhs** or **sobol** for screening in higher dimension.
- Use **sobol_saltelli** only when you intend to compute Sobol indices.
- Use **adaptive_refine** when you care about steep boundaries or regime changes.
- Use **bayesopt** when you want to optimize one scalar metric rather than map the whole surface.
- Increase `runs_per_point` before increasing design complexity if Monte Carlo noise dominates your metric.
